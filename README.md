# agent_nirs — LLM, инструменты, харнесс и MCP на Go

Четыре программы, которые по шагам показывают, чем отличаются:

1. **LLM + инструменты** (без харнесса);
2. **LLM + харнесс** (без инструментов);
3. **LLM + харнесс + локальные инструменты**;
4. **LLM + харнесс + инструменты по MCP** (вместе с локальными).

Код написан только на стандартной библиотеке Go. Пакеты и типы названы по
терминам из глоссария НИРС, а в doc-комментариях пакетов приведены сами определения.

## Чем отличаются варианты

| | 1. LLM + инструменты | 2. LLM + харнесс | 3. + локальные инструменты | 4. + MCP-инструменты |
|---|---|---|---|---|
| Модель получает описания инструментов | да | нет | да | да |
| Кто выполняет вызов инструмента | **никто** | — | харнесс, внутри программы | харнесс: локальные сам, MCP через MCP-клиент на MCP-сервере |
| Цикл агента (LLM → шаг → результат → LLM) | нет, один вызов | есть, но всегда 1 шаг | есть | есть |
| История между запросами | нет (LLM stateless) | да | да | да |
| Память (релевантные данные в контексте) | нет | да | да | да |
| Skills (каталог + `load_skill`) | нет | нет | да | да |
| Проверка запроса на валидность и безопасность | нет | да | да | да |
| Лимиты, сжатие контекста | нет | да | да | да |
| Подтверждение опасных вызовов | нет | — | да | да (`delete_message`) |

Главное:

- **1 → 2.** Сама LLM ничего не выполняет и ничего не помнит. Она лишь
  возвращает текст или вызов инструмента (имя и параметры). В варианте 1 видно,
  что вызов просто печатается: исполнить его некому.
- **2 → 3.** Харнесс получает инструменты, и цикл агента становится полным:
  модель предлагает вызов, харнесс проверяет и выполняет его, кладёт результат
  в контекст и снова вызывает модель.
- **3 → 4.** Код харнесса не меняется. Добавляется ещё один источник
  инструментов, MCP-клиент (`mcp.Client` реализует тот же интерфейс
  `tools.Toolbox`, что и `LocalToolbox`). Модель видит одинаковые описания
  и не может отличить локальный инструмент от MCP-инструмента. Где выполнять
  вызов, решает харнесс.

## Как устроено (термины → код)

| Термин | Где в коде |
|---|---|
| LLM | `internal/llm`: один вызов `Complete(messages, tools)`, состояния нет |
| Инструмент (name, description, input_schema, required) | `internal/tools.Tool` |
| Список инструментов | `context.Tools`, собирается харнессом из всех `Toolbox` |
| Вызов инструмента | `llm.ToolCall`: модель возвращает имя и параметры |
| Результат инструмента | `tools.Result`, попадает в контекст как сообщение `role: tool` |
| Локальный инструмент | `tools.LocalToolbox`, `internal/localtools` |
| MCP | `internal/mcp/protocol.go`: HTTP + JSON-RPC 2.0 (`initialize`, `tools/list`, `tools/call`) |
| MCP-сервер | `internal/mcp/server.go`, `cmd/mcp_mail_server` |
| MCP-клиент | `internal/mcp/client.go` |
| Постоянное хранилище | `memory.Storage`: файл `data/memory.json` |
| Память | `memory.Memory.Relevant`: в контекст идут только релевантные записи; модель о памяти не знает |
| Skill | `internal/skills`, папка `skills/`: в контексте только название и описание, текст загружает `load_skill` |
| Контекст | `internal/agentcontext`: системный промпт, инструменты, каталог skills, память, краткое содержание, история |
| Системный промпт, критерии завершения | `internal/prompt` |
| Лимиты | `harness.Limits`: шаги, токены, длина запроса, размер истории |
| Цикл агента | `harness.Run` |
| Харнесс | `internal/harness`: проверки, сборка контекста, выполнение и маршрутизация вызовов, подтверждение, сжатие контекста |

Цикл агента в `harness.Run`:

```
запрос → проверка на валидность → проверка на безопасность → сборка контекста
  └─ цикл (пока не исчерпаны лимиты):
       управление контекстом (сжать старую историю)
       LLM(контекст) → ответ
       текст?           → критерии завершения выполнены, вернуть ответ
       вызов инструмента → харнесс: инструмент существует? параметры верны?
                            опасный? → спросить пользователя
                            локальный → выполнить сам; MCP → tools/call через MCP-клиент
                            результат → в контекст
```

## Запуск

Нужен Go 1.22+ и любой OpenAI-совместимый API.

```bash
export LLM_BASE_URL=https://api.openai.com/v1   # или http://localhost:11434/v1 для Ollama
export LLM_API_KEY=sk-...                        # для Ollama любая строка
export LLM_MODEL=gpt-4o-mini                     # для Ollama, например, qwen2.5:7b
```

```bash
# 1. LLM + инструменты: модель вернёт вызов, но выполнять его некому
go run ./cmd/01_llm_tools "Какая погода в Казани?"

# 2. LLM + харнесс: диалог с историей и памятью, без инструментов
go run ./cmd/02_llm_harness
#   > запомни: я болею за Рубин
#   > За какую команду я болею?

# 3. LLM + харнесс + локальные инструменты
go run ./cmd/03_harness_local_tools
#   > Какая погода у меня в городе?   (город берётся из памяти, skill weather_report)

# 4. LLM + харнесс + MCP-инструменты
go run ./cmd/mcp_mail_server            # отдельный терминал: MCP-сервер почты на :8000
go run ./cmd/04_harness_mcp_tools
#   > Есть письма от начальника?        (адрес начальника берётся из памяти)
#   > Удали рекламное письмо            (харнесс спросит подтверждение)
```

Каждая программа пишет ход работы в stderr: строки `[LLM]` — что предложила
модель, `[харнесс]` — что сделал харнесс, `[MCP-сервер]` — что выполнил сервер.
Если передать запрос аргументами, он выполнится один раз; без аргументов
запускается диалог.

## Замечания

- MCP реализован вручную (HTTP + JSON-RPC 2.0, подмножество транспорта
  Streamable HTTP), чтобы было видно, что это за протокол. Реализация
  совместима с официальным SDK: Go-клиент работает с сервером на Python SDK
  (`FastMCP`, ответы в SSE), а Python-клиент — с Go-сервером. В реальном
  проекте вместо `internal/mcp` стоит взять официальный
  [github.com/modelcontextprotocol/go-sdk](https://github.com/modelcontextprotocol/go-sdk).
- Релевантность памяти считается по совпадению слов. В RAG вместо этого
  используют эмбеддинги и векторную базу.
- Проверка на безопасность — простой поиск признаков промпт-инъекции по
  регулярному выражению. Она показывает, в каком месте цикла стоит проверка.
- Данные погоды и почты выдуманные.

## Структура

```
cmd/
  01_llm_tools/            вариант 1
  02_llm_harness/          вариант 2
  03_harness_local_tools/  вариант 3
  04_harness_mcp_tools/    вариант 4
  mcp_mail_server/         MCP-сервер почты
internal/
  llm/           клиент LLM (OpenAI-совместимый /chat/completions)
  tools/         инструмент, результат, Toolbox, локальные инструменты
  localtools/    get_weather, get_current_time
  mcp/           протокол, MCP-сервер, MCP-клиент
  memory/        постоянное хранилище и память
  skills/        загрузка skills
  agentcontext/  контекст
  prompt/        системный промпт
  harness/       харнесс и цикл агента
  cli/           диалог в терминале и подтверждение
skills/          weather_report, inbox_digest
data/memory.json пример памяти
```
